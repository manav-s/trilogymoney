## 1. Executive Summary

Trilogy is a privacy-first financial awareness application that provides users with daily text message updates about their financial status. This document outlines our comprehensive information security policy, demonstrating our commitment to protecting user data and maintaining the highest standards of security and privacy.

### 1.1 Policy Scope
This policy applies to:
- All Trilogy systems and infrastructure
- All future employees, contractors, and third-party service providers (only myself, Manav Sharma for now)
- All user data processed by Trilogy
- All integrations with third-party services (Plaid, Clerk, Vercel, Neon, Blooio)

### 1.2 Our Security Commitment
We commit to:
- Protecting user financial data with industry-leading encryption
- Never storing sensitive transaction details or account balances
- Implementing defense-in-depth security practices
- Maintaining transparency about our data handling
- Continuous security monitoring and improvement

## 3. Data Classification & Handling

### 3.1 Data Classification Levels

#### Critical - Encrypted Access Tokens
- **Definition:** Plaid access tokens that enable bank account access
- **Storage:** AES-256-GCM encrypted in database
- **Access:** Decrypted only at runtime for API calls
- **Retention:** Until user disconnects or deletes account
- **Logging:** Never logged in decrypted form

#### High - User Authentication Data
- **Definition:** Phone numbers, verification codes, session tokens
- **Storage:** Managed by Clerk (third-party auth provider)
- **Access:** Via secure API calls only
- **Retention:** Per Clerk's retention policy
- **Logging:** Authentication events only (no credentials)

#### Medium - User Profile Data
- **Definition:** Name, timezone, preferences, settings
- **Storage:** Encrypted at rest in Neon PostgreSQL
- **Access:** Application layer with authenticated requests
- **Retention:** Until account deletion
- **Logging:** Access logs retained for 30 days

#### Low - Usage Analytics
- **Definition:** Aggregated, anonymized usage statistics
- **Storage:** Analytics platform (anonymized)
- **Access:** Dashboard access for authorized team
- **Retention:** 1 year
- **Logging:** Standard analytics logging

### 3.2 Data We Do NOT Store
To minimize risk, we explicitly do NOT store:
- ❌ Transaction details (merchants, dates, amounts)
- ❌ Historical account balances
- ❌ Bank account numbers or routing numbers
- ❌ Bank login credentials (handled by Plaid)
- ❌ Credit card numbers
- ❌ Social security numbers
- ❌ Driver's license numbers

### 3.3 Data Minimization Principle
We only collect and retain data necessary to:
1. Provide the core service (daily financial updates)
2. Authenticate users securely
3. Send text messages
4. Respond to customer support inquiries
5. Comply with legal obligations

All other data is calculated in real-time and immediately discarded.

## 4. Technical Security Controls

### 4.1 Encryption Standards

#### Data at Rest
- **Algorithm:** AES-256-GCM (Galois/Counter Mode)
- **Key Management:** 
  - Encryption keys stored in environment variables
  - Keys are 32-byte (256-bit) length
  - Key rotation capability implemented
  - Keys never committed to version control
- **Scope:** All sensitive data in database (access tokens, user data)

#### Data in Transit
- **Protocol:** TLS 1.3 (minimum TLS 1.2)
- **Certificate Authority:** Let's Encrypt (managed by Vercel)
- **Cipher Suites:** Modern, secure ciphers only (no deprecated algorithms)
- **HTTPS:** Enforced for all connections
- **HSTS:** HTTP Strict Transport Security enabled

#### Encryption Implementation
```
Plaid Access Token Storage:
1. Token received from Plaid API
2. Encrypted using AES-256-GCM with unique IV
3. Stored as: IV:AuthTag:EncryptedData
4. Decrypted only when needed for API calls
5. Never logged or cached in decrypted form
```

### 4.2 Authentication & Access Control

#### User Authentication
- **Provider:** Clerk (SOC 2 Type II certified)
- **Method:** Phone number + SMS verification code
- **Session Management:** Secure JWT tokens with expiration
- **Session Duration:** 7 days with automatic refresh
- **Multi-device:** Supported with secure session handling

#### Team Access Control
- **MFA Required:** Yes, for all production access
- **Password Policy:** 
  - Minimum 12 characters
  - Complexity requirements enforced
  - Regular rotation encouraged
- **Role-Based Access Control (RBAC):**
  - Admin: Full system access
  - Developer: Code repository + staging environment
  - Support: Read-only user data access (with audit trail)
- **Principle of Least Privilege:** Users granted minimum necessary access

#### API Security
- **Authentication:** Bearer tokens (via Clerk)
- **Rate Limiting:** 
  - 100 requests per minute per user
  - 1000 requests per hour per user
  - Graduated backoff for violations
- **Input Validation:** All inputs sanitized and validated
- **SQL Injection Prevention:** Prisma ORM with parameterized queries

### 4.3 Infrastructure Security

#### Cloud Architecture
```
User's Phone
    ↓ (TLS 1.3)
Blooio SMS Gateway
    ↓ (HTTPS)
Vercel Edge Network (Serverless)
    ↓ (Encrypted connection)
Neon PostgreSQL (Encrypted storage)
```

**Serverless Benefits:**
- No persistent servers to patch
- Automatic scaling with built-in DDoS protection
- Isolated execution environments
- Managed by SOC 2 certified providers

#### Service Providers & Certifications

| Provider | Purpose | Certifications |
|----------|---------|----------------|
| **Vercel** | Application hosting | SOC 2 Type II, ISO 27001 |
| **Neon** | PostgreSQL database | SOC 2 Type II, GDPR compliant |
| **Clerk** | Authentication | SOC 2 Type II, GDPR compliant |
| **Plaid** | Bank connectivity | SOC 2 Type II, ISO 27001, PCI DSS |
| **Blooio** | SMS/iMessage delivery | [Certification status to be verified] |

#### Network Security
- **Firewall:** Managed by cloud providers (Vercel, Neon)
- **DDoS Protection:** Vercel's built-in protection + rate limiting
- **IP Allowlisting:** Not required (serverless architecture)
- **VPN Access:** Not applicable (no corporate network)
- **Intrusion Detection:** Cloud provider monitoring + application logging

### 4.4 Application Security

#### Secure Development Lifecycle
1. **Code Review:** All changes reviewed before merge
2. **Dependency Scanning:** 
   - `npm audit` run weekly
   - Dependabot automated updates enabled
   - Critical vulnerabilities patched within 48 hours
3. **Static Analysis:** TypeScript strict mode enforced
4. **Security Testing:** Manual security review for auth & payment flows
5. **Deployment:** Automated CI/CD with security checks

#### Secure Coding Practices
- **Input Validation:** All user inputs sanitized
- **Output Encoding:** XSS prevention
- **Parameterized Queries:** SQL injection prevention (Prisma ORM)
- **Error Handling:** Secure error messages (no sensitive data leaked)
- **Logging:** Security events logged, sensitive data never logged
- **CSRF Protection:** Built into Next.js framework

#### Third-Party Dependencies
- **Package Management:** npm with package-lock.json
- **Vulnerability Scanning:** GitHub Dependabot + npm audit
- **Update Policy:** 
  - Critical security updates: Within 48 hours
  - High priority updates: Within 1 week
  - Regular updates: Monthly review
- **Vendor Assessment:** Security review before integrating new dependencies

### 4.5 Database Security

#### Neon PostgreSQL Security
- **Encryption at Rest:** AES-256 encryption (managed by Neon)
- **Encryption in Transit:** TLS for all connections
- **Access Control:** 
  - Connection string stored in environment variables
  - No public database access
  - Application-only access via Prisma ORM
- **Backups:** 
  - Automated daily backups (managed by Neon)
  - 30-day retention
  - Encrypted backup storage
- **Monitoring:** Query performance and error monitoring

#### Data Isolation
- **Production Environment:** Completely isolated
- **Staging Environment:** Separate database with test data only
- **Development Environment:** Local databases, no production data

## 6. Data Privacy & Compliance

### 6.1 Privacy-First Architecture
Our architecture is designed around data minimization:

#### Real-Time Processing
```
User requests daily update
    ↓
Fetch current balance from Plaid (real-time)
    ↓
Calculate spending from recent transactions (real-time)
    ↓
Generate message with calculated numbers
    ↓
Send via SMS
    ↓
Discard all financial data (nothing stored)
```

#### What Gets Stored vs. Calculated
**Stored:**
- ✅ Encrypted Plaid access token
- ✅ User preferences (name, phone, timezone)
- ✅ Conversation messages (60-day retention, AES-256-GCM encrypted)
- ✅ Bank connection metadata (bank name, account type)

**Calculated in Real-Time (Not Stored):**
- ⚡ Current account balance
- ⚡ Yesterday's spending (from transactions)
- ⚡ This week's spending (from transactions)
- ⚡ Transaction details (merchants, amounts, dates)

### 6.2 User Rights & Control

#### User Data Rights (CCPA/GDPR Compliant)
- **Right to Access:** Users can view all stored data
- **Right to Delete:** Users can delete account and all data
- **Right to Portability:** Users can export data in JSON format
- **Right to Opt-Out:** Users can disable messages anytime
- **Right to Rectification:** Users can update their information
- **Right to Be Forgotten:** Complete data deletion within 30 days

#### User Control Features
- **Bank Disconnection:** Instant access token revocation
- **Message Pause:** Temporarily disable messages
- **Account Deletion:** Self-service account deletion
- **Data Export:** Download all personal data
- **Preference Management:** Update delivery time, settings

### 6.3 Messaging (Blooio)
- **Message Delivery:** SMS/iMessage delivery via Blooio API
- **Message Storage:** Conversation history retained for 60 days, then auto-deleted
- **Message Content:** May include financial information user chooses to share
- **Encryption:** All messages encrypted at rest using AES-256-GCM
- **Privacy:** Messages encrypted in transit (TLS 1.3) and at rest (AES-256-GCM)
- **User Control:** Users can disable conversational features anytime

### 6.4 Third-Party Data Sharing

#### Plaid (Bank Connectivity)
- **Data Shared:** Encrypted access token for API authentication
- **Purpose:** Fetch real-time balance and transaction data
- **Data Flow:** Plaid → Trilogy (real-time calculation) → User
- **Storage:** Only access token stored (encrypted)
- **User Control:** Users can disconnect bank anytime

#### Clerk (Authentication)
- **Data Shared:** Phone number for authentication
- **Purpose:** User verification and session management
- **Storage:** Managed by Clerk per their privacy policy
- **Security:** SOC 2 Type II certified

#### Blooio (Messaging)
- **Data Shared:** Phone number and message content
- **Purpose:** SMS/iMessage delivery
- **Storage:** Messages not retained after delivery
- **Privacy:** Encrypted in transit

#### OpenAI or Other LLM Providers (Conversational AI)
- **Data Shared:** User questions and calculated financial data (real-time)
- **Purpose:** Generate conversational responses
- **Storage:** Per provider's data retention policy (typically not stored for training)
- **Privacy:** No stored transaction data sent, only real-time calculations

**Data Never Shared:**
- ❌ Raw transaction data
- ❌ Account balances (except in real-time calculations)
- ❌ Bank credentials
- ❌ User data for advertising or marketing purposes

### 6.5 Compliance Framework

#### United States
- **GLBA (Gramm-Leach-Bliley Act):** 
  - Privacy notices provided
  - Data security measures implemented
  - Opt-out rights available
- **State Privacy Laws (CCPA, Virginia CDPA, etc.):**
  - User rights honored (access, delete, opt-out)
  - Privacy policy published and accessible
  - "Do Not Sell" option provided (though we don't sell data)

#### International (If Applicable)
- **GDPR (EU):** 
  - Legal basis for processing (user consent/contract)
  - Data subject rights (access, deletion, portability)
  - Data protection by design
  - Right to lodge complaint with supervisory authority

### 6.6 Data Breach Notification

#### Breach Response Plan
1. **Detection & Containment:** Immediate isolation of affected systems
2. **Assessment:** Determine scope, affected users, data types
3. **Notification Timeline:**
   - Users: Within 72 hours of discovery (GDPR requirement)
   - Regulators: Per applicable law (typically 30-60 days)
   - Law enforcement: If criminal activity suspected
4. **Communication:** 
   - What happened
   - What data was affected
   - Steps we're taking
   - Steps users should take
5. **Remediation:** Fix vulnerability, enhance security
6. **Post-Mortem:** Document lessons learned, update policies

#### Notification Thresholds
A breach notification is triggered if:
- Unauthorized access to encrypted or unencrypted personal data
- Exposure of financial data
- Compromised authentication credentials
- System intrusion with potential data exposure

## 8. Incident Response

### 8.1 Security Incident Classification

#### Severity Levels
**Critical (P0):**
- Active data breach or unauthorized access
- Production system compromise
- Encryption key exposure
- Widespread service outage

**High (P1):**
- Suspected security incident
- Elevated suspicious activity
- Failed security controls
- Partial service degradation

**Medium (P2):**
- Security misconfiguration discovered
- Failed login attempts pattern
- Minor vulnerability identified
- Non-critical system issue

**Low (P3):**
- Security policy violation
- Minor security concern
- Informational security event

### 8.2 Incident Response Process

#### Phase 1: Detection & Analysis
- Incident identified via monitoring, user report, or security scan
- Initial assessment and classification
- Document timeline and evidence
- Determine if incident is security-related

#### Phase 2: Containment
- **Immediate containment:** Isolate affected systems
- **Short-term containment:** Apply temporary fixes
- **Evidence preservation:** Capture logs, snapshots
- **Notification:** Alert security officer and relevant team members

#### Phase 3: Eradication
- Identify root cause
- Remove threat (malware, unauthorized access, etc.)
- Patch vulnerabilities
- Verify systems are clean

#### Phase 4: Recovery
- Restore systems from clean backups if needed
- Verify functionality and security
- Monitor for recurrence
- Gradual return to normal operations

#### Phase 5: Post-Incident
- **Incident Report:** Document what happened, response actions, outcomes
- **Lessons Learned:** What went well, what needs improvement
- **Policy Updates:** Update security policies and procedures
- **Training:** Additional training if needed
- **User Communication:** Transparent communication with affected users

### 8.3 Incident Communication

#### Internal Communication
- **Security Officer:** Immediate notification for P0/P1 incidents
- **Development Team:** As needed for technical response
- **Leadership:** For incidents requiring business decisions

#### External Communication
- **Affected Users:** Within 72 hours (per GDPR)
- **Regulators:** Per legal requirements (typically 30-60 days)
- **Vendors:** If vendor systems implicated
- **Media:** Only for significant incidents, coordinated response

#### Communication Templates
Pre-approved templates for:
- User breach notifications
- Regulatory notifications
- Internal incident alerts
- Status page updates

### 10.3 Failure Scenarios & Response

#### Scenario 1: Vercel Outage
- **Detection:** Monitoring alerts + user reports
- **Impact:** Application unavailable
- **Response:** Status page update, wait for Vercel recovery
- **Mitigation:** Consider multi-cloud strategy for future

#### Scenario 2: Database Outage
- **Detection:** Failed database connections
- **Impact:** Application unavailable
- **Response:** Contact Neon support, restore from backup if needed
- **Mitigation:** Point-in-time recovery capability

#### Scenario 3: Plaid API Issues
- **Detection:** Failed API calls
- **Impact:** Cannot fetch user financial data
- **Response:** Queue messages for retry, notify users of delay
- **Mitigation:** Implement retry logic with exponential backoff

#### Scenario 4: SMS Delivery Failure
- **Detection:** Failed message delivery status
- **Impact:** Users don't receive daily messages
- **Response:** Retry delivery, investigate Blooio status
- **Mitigation:** Implement fallback messaging channel

### 10.4 Communication During Outages
- **Status Page:** Real-time status updates at status.trytrilogy.com
- **User Notifications:** SMS notification if prolonged outage
- **Estimated Resolution:** Provided when available
- **Post-Mortem:** Published after significant incidents
